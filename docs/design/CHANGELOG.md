## Q12 ヒアリング結果

- **回答: C** — MacがオフラインならVPSが作業指示を**期限付きで永続保留**し、有効期限内の再接続・認可・セッション準備完了で自動配送する。期限を過ぎた未配送指示は**実行せず**元窓口へ失効を通知する。
- **対象:** 秘書の `project_pm_send→pm_send`（WebChat・Discord）とWebChatの `thread_direct_send`（PM／子への直接指示）。後者もオフラインで保留する変更であり、Q4/Bの「即時エラー」記載を改めた。承認回答、CU端末選択、停止・中断、設定は保留対象外。
- **責務:** VPSが `expires_at` をUTCで発行して `offline-requests.jsonl` に永続保存。Mac再接続時、認可・案件・セッションを検査し、デーモンもチャネル投入前に期限を確認。子への直接指示とPM通知はMac側で原子的に登録。
- **二重配送:** `request_id`／`message_id` を安定した指示キーとして使用し、Macの永続受信台帳と照合。Claudeへの配送が確定しない場合は `delivery_unknown` として盲目的な自動再実行を避ける。Strict Exactly-onceまで実証した扱いにはしない。
- **返答:** オフライン保留は `pending_offline` であり配送・実行・完了とは別。期限切れは `expired`。Discordへの失効通知も、送信直前の許可検査とDM禁止を維持し、送信不可ならWebChat内の履歴で知らせる。
- **設定:** `hub.json` に `offline_queue.enabled`、`ttl_minutes`、`max_pending_per_worker`、`events_path` を追加して **未実装v8案**へ更新。worker.jsonはv2未実装案のまま。通信proto2未実装案には `expires_at`・受理/失効/不明ステータスを追加する。
- **Q12時点で未確定だった項目:** TTLの具体的な時間は次のQ13で決めることとしていた（**Q13/Cで24時間＝1,440分に確定済み**）。OSS初期設定は `enabled=false`。容量100件／Macは仮の実装上限であり最終決定ではない。
- **実装・検証:** 設計書の変更のみ。VPS・Macの永続キュー、発行元への失効通知、復帰時の二重実行抑止は未実装・未検証。
