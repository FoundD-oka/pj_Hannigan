## 1. 目的

利用者は WebChat または Discord で VPS 上の論理的に一つの統括秘書と会話できる。**物理的な Claude Code 対話セッションは WebChat の会話 ID・Discord の許可サーバーチャンネル／スレッドごとに分離し、共通の案件台帳のみ参照する（Q6/B）。**統括秘書が担当 Mac と案件を選び、
その Mac 上の案件別 PM Claude Code に指示する。案件 PM は軽量な調査・小規模修正を自ら行い、長時間・並列・GUI 操作を伴う作業を同じ Mac の子作業セッションへ委任する。どちらの経路でも PM が結果を統括秘書へ報告する。
利用者は **WebChat 限定**で案件 PM と各子セッションのスレッドを開き、実行状況・取得可能な会話履歴を閲覧し、どちらにも直接追加指示できる。子への直接指示は担当 PM にも通知し、PM の案件責任と報告経路を維持する。**Discord は統括秘書への通常の指示・相談と秘書からの返信のみを扱い、個別セッションを直接操作する窓口にはしない（Q5/A）。許可チャンネルでは共有案件台帳の全案件を参照できる（Q7/C）。メッセージの起動条件はBotへの明示メンションまたはBot自身の投稿への返信のみ（Q8/A）。許可利用者全員が、許可チャンネルから統括秘書経由で登録済み案件PMに実作業を依頼できる（Q9/A）。Discordの個人DM・グループDMは利用しない（Q10/A）。Discordからの実作業依頼は、受信・委任の認可を通過すれば追加の着手承認なしに案件PMへ配送する（Q11/A）。Claude Codeが要求するツール承認とCU等の既存承認は維持する。** Q12/C・Q13/C:** Macがオフラインの場合、秘書から案件PMへの依頼とWebChatから個別PM／子スレッドへの直接指示をVPSで**受付から24時間（1,440分）**保留し、期限内に対象の再接続と再認可が成立したときだけ自動配送する。期限切れは未実行として通知する。
GUI 操作が必要な作業は各 Mac の純正 Computer Use（以下 CU）で行う。
最終的に OSS として公開するため、設定は利用者が設定画面から行い、コードには埋め込まない。

| 部品 | 動く場所 | 正体 | 役割 |
| --- | --- | --- | --- |
| WebChat UI | ブラウザ（VPS が配信） | 静的ページ | **メイン窓口**。秘書との会話、案件／PM／子スレッドの一覧・履歴表示と直接投稿、進捗・承認・停止・設定 |
| Discord Bot アダプター | VPS（ハブと同じ環境） | Discord とハブの間の接続モジュール／常駐プロセス | **サブ窓口**。認可済み Discord メッセージを統括秘書への通常会話として受け渡し、秘書の返答を元の Discord 会話へ返す。PM／子への直接送信・承認・設定・ターミナル操作は提供しない |
| ハブ | VPS（原則 Linux） | 常駐プログラム兼 秘書用チャネルサーバー | WebChat の配信、Discord アダプターの内部受信口、会話コンテキストごとの秘書セッション管理、認可付き共有案件台帳、ワーカー接続、期限付きオフライン依頼キュー／失効通知、依頼元ごとの返信ルーティング、各作業スレッドの履歴集約、**WebChat 限定**の直接指示 API |

| 案件別 PM Claude | 案件を保持する Mac | Claude Code の対話セッション（`role=pm`） | 案件資料を把握し、軽量な調査・小規模修正は自身のツールで実行。長時間・並列・GUI 作業は子セッションに委任し、品質確認と報告を担う。子への人間の直接介入通知を受け取り、作業計画・重複実行を調整する |
| 作業 Claude | 案件別 PM と同じ Mac | Claude Code の対話セッション（`role=task`） | 案件 PM の指示によって調査・実装・純正 CU の作業を行う |

| セッション別チャネル | 作業 Mac | Claude Code が起動するチャネルサーバー | PM と作業セッションで同じブリッジを使用し、`role` ごとに公開ツールを制限する |

Claude 同士は直接通信しない。すべてハブと常駐プログラムが仲介する。

## 3. 接続の向き

```text
WebChat（秘書＋PM／子の閲覧・直接介入）    Discord（秘書との会話のみ）
             │ HTTPS/SSE                           │ Bot 接続
             ▼                                     ▼
     VPS Hannigan Hub ◄── localhost ── Discord Bot アダプター
             ▲   │
             │   ├── localhost／ブリッジ ── 統括秘書 Claude Code × 会話コンテキスト
             │   │                              （各会話は独立セッション）
             │   ├── 共通案件台帳（進捗・タスク）← 認可して参照／更新
             │   └── オフライン依頼キュー（有効期限・配送結果・失効通知）
             │ WSS（各 Mac 側から接続）
             │
     Mac ワーカー常駐プログラム
             │ localhost／セッション別ブリッジ
             ├──► 案件 PM Claude Code ─── 自身の組み込みツール（軽量な作業）
             │          ▲    │
             │          │    └─ ローカルデーモンへ委任
             │          │                  ▼
             └──────────┴──── 作業 Claude Code × N（原則ここで純正 CU）
              （WebChat から子への直接介入は PM にも通知）
```

- Channels は「チャネルサーバーを起動した Claude Code の 1 セッションに出来事を流し込む」一方向の仕組み。
  セッションから外へ送るのは返信ツールなどの通常のツール呼び出しで行う
- 作業 Mac は VPS 上のハブへ自分から接続する（接続型）。Mac 側のポート開放は不要。異なるネットワークからは WSS（HTTPS/TLS 終端）を使う
- チャネルは PM／作業セッションごとに 1 プロセス。常駐プログラムが VPS ハブとの 1 本の接続に集約する
- **案件 PM と作業セッションは同じ Mac・同じ案件フォルダに属する独立した Claude Code 対話セッション**。PM → 作業の指示は Claude 同士の直接接続ではなく、同じ Mac のワーカー常駐プログラムが仲介する
- ハブと秘書 Claude は VPS 上で実行する。秘書は純正 CU を使用しない。純正 CU は Mac 上の対話セッションで実行する
- VPS 上の秘書は**会話ごとの対話セッション**としてハブがオンデマンド起動・再開し、セッションごとのローカルブリッジで通信する。VPS 自身を Mac ワーカーとして扱わない。
- **人間による個別スレッドへの指示は、統括秘書を経由して文章を再生成するのではなく、認証済み WebChat → VPS ハブ → 対象ワーカーのチャネルへ送る。** 子への直接指示は同じ Mac 上の案件 PM にも事実として通知する
- **Discord は**新たな統括秘書の人格や専用 PM を作らず、既存の統括秘書役割への会話入口にする。ただし WebChat・Discord の各会話は**別の秘書 Claude Code セッション**として分離する。Discord Adapter は VPS 内部の受信インターフェースのみ使用し、ワーカー／個別スレッド API に直接アクセスできない。

## 4. 主な流れ

### 4.1 会話から作業まで

1. 利用者が WebChat または許可済み Discord から投稿。VPS ハブは認証された受信場所から `context_id` を特定し、その会話専用の統括秘書 Claude Code セッションへ `<channel>` として届ける。Discord の投稿は PM／子への直接投稿としては扱わない。
2. 秘書が認可済みの共有案件台帳などから `worker` と `project` を選び、`project_pm_send` を呼ぶ。ハブが `request_id` と依頼元 `context_id` を保存し、ワーカーがオンラインなら `pm_send` を送る。**Q12/C:** オフラインならVPS上の期限付き永続キューに `pending_offline` として受理し、`expires_at` も依頼元へ返す（PMへの配送／実行は未了）。**Q11/A:** Discordの認可済み実作業依頼について、これとは別の「高影響なら着手前にWebChat承認」という待ち状態・承認ゲートを設けない。既存のClaude Codeツール承認は作業実行時に適用する。
3. ワーカー常駐プログラムがその案件の PM を特定。未起動なら作成、停止済みなら再開し、PM セッションへ指示を流し込む。同じワーカーの `(worker_id, project_id)` に PM は原則 1 つ。
4. 案件 PM は内容・所要時間の見込み・並列化の必要性・GUI/CU の有無を確認し、**直接実行**か**子セッションへの委任**かを判断する。
5. **直接実行の場合:** PM が自分の Claude Code の組み込みツールで軽量調査や小規模修正を行い、検証してから `reply` で報告する。子セッションは作らない。
6. **委任の場合:** PM が同じ案件の作業セッションへローカル MCP ツール（`task_create` / `task_send` など）で指示。子が `reply` を呼ぶとデーモンが**担当 PM セッションへ結果を通知**する。子の状態・報告は VPS ハブにも記録する。
7. PM は自分の実行結果または子の成果物を確認し、`request_id` を付けた `role=pm` の `session_report` で統括秘書へ報告する。PM は共有台帳の進捗・タスク状態を構造化イベントで起票・更新できる。必要なら複数回進捗を報告できる。
8. ハブは `request_id` で元の**秘書会話セッション**を特定して PM 報告を通知。秘書は元の依頼に紐づく **WebChat または Discord の送信元**へ回答する。送信元が特定できなければ別会話に推測配送せず保留する。

既存の `session_create` / `session_send` 等はデーモンの基本機構として保持する。**通常の新規依頼の宛先は案件 PM**。一方、利用者が WebChat で特定の PM／子スレッドを選択した場合は、その対象に直接送信する（Q4/B）。

### 4.1.1 PM の実行／委任ポリシー（Q3/B 確定）

| 選択 | 目安 | 実行主体 |
| --- | --- | --- |
| PM が直接実行 | 単発の調査、短い仕様確認、小規模で独立したコード修正、簡単なテスト | `role=pm` の Claude Code。通常のツール承認が必要な操作は従来どおり承認を求める |
| 子セッションへ委任 | 複数段階の実装、長時間作業、並列化したい作業、純正 CU による GUI 操作 | `role=task` の Claude Code。PM が開始・結果確認・報告を担当 |
| 迷う／同時編集の可能性がある | ファイルの競合、範囲不明、破壊的変更の恐れ | まず PM が調査・作業範囲を絞り、必要なら委任。承認を迂回しない |

- 判断は PM の裁量と案件ごとの `projects[].pm.execution_policy`、`extra_instructions` に従う。秒数・トークン数・コード行数による絶対しきい値は、ユーザー要件として確定していないため設定しない。
- **純正 CU は既定運用で子セッションへ委任する。** PM 自身の軽量なコード操作は許可するが、CU の利用はQ14/BによりMacのデーモンが排他調整する設計とし、同時に1セッションに限る。純正CUのロックがセッション終了まで続く可能性を考慮し、作業単位の短いロックだけで解放しない。PM の CU 利用禁止や排他の強制可否は要実機検証（指示文だけを安全な境界と扱わない）。
- 同じ案件フォルダを PM と子が共有することは独立した作業領域を意味しない。**Q15/BでGit worktreeを作らず、同じ実体フォルダの書込可能セッションを最大1つに直列化する方式を確定した。**技術的な強制が検証されるまでは同一領域に複数の書込可能セッションを走らせない（4.1.12）。
- `role=task` は案件 PM への成果報告を担当し、`task_*` の再委任ツールを公開しない。PM が直接処理した場合も委任した場合も、VPS 統括秘書から見た案件の窓口は PM で統一する。

**暫定の案件所有規約:** `worker_id` と `project_id` の組を案件 PM の所属先とする。ひとつの論理案件を複数 Mac で共有する場合の主担当や PM 間連携は Q2/B だけでは決まらないため、未確定として残す。

### 4.1.2 WebChat から PM／子スレッドへの直接介入（Q4/B 確定）

1. WebChat にワーカー → 案件 → PM と子セッションの一覧を表示する。PM／子それぞれの独立したスレッドを開き、会話メッセージ、指示の配送状況、報告、状態・承認履歴を確認できるようにする。**Claude の非公開の推論や未取得の操作履歴まで見えると主張しない。**
2. 利用者が PM スレッドに直接投稿した場合、ハブが投稿者・対象・`msg_id` を確定し、対象 PM のチャネルへ届ける。統括秘書の再解釈を挟まず、既存の案件 PM が通常どおり回答・作業を管理する。
3. 利用者が子スレッドに直接投稿した場合、同じ本文を対象子へ届けるとともに、担当 PM には **「利用者が子へ直接介入した」という事実通知**を別配送する。通知には対象子、元の `msg_id`、指示本文、配送状態を含める。PM は指示を再送せず、作業の重複・矛盾を確認して計画と報告に反映する。
4. 子への指示と PM への通知の配送状態は個別に追跡する。PM が一時停止／不在なら通知を永続キューに保持し、再開後に届ける。Q12/C によりワーカーがオフラインなら、ハブ側で対象子とPM所属を検証した上で期限付きキューに保留する。画面には `pending_offline` と期限を表示し、**子への配送成功やPMへの通知成功とは区別する**。
5. WebChat の直接投稿・会話履歴取得・イベント購読は、対象ワーカー／案件／セッションのアクセス権をハブ側で再検証する。デーモンも `role` と PM 所属を確認し、引数にある任意の `pm_session` を信用しない。全操作は監査用イベントとして残す。

**返信の経路:** PM／子が `reply` した内容はそれぞれのスレッドにも表示する。秘書経由の案件依頼に紐づく PM 報告だけを統括秘書へ通常報告として流し、人間から PM へ直接送ったメッセージへの返信は PM スレッドを第一の表示先にする。子の `reply` は従来どおり PM にも届く。返信と元指示の紐づけが曖昧な場合は、勝手に秘書チャットへ転送せずスレッドに表示する。

**表示できる履歴の範囲:** Hannigan 経由のユーザー指示、Claude の `reply`、セッション状態、承認・配送イベントは本仕様で取得対象にする。Claude Code 本体の中間発言・ツール実行を表示するには、Mac 上のネイティブなセッション記録等を読み取る専用アダプターが追加で必要。対象版で完全性・追従遅延・重複排除・秘密情報の除外を検証し、取得できない部分は WebChat に明示する。**最終返信しか見えない画面を「作業スレッド全体の閲覧完了」として検収しない。**

**Q4/B の範囲外:** tmux ターミナル画面の直接表示・キー入力操作は許可しない（Q4/C 相当）。通常の承認／中断／停止 UI は維持する。

### 4.1.3 Discord を統括秘書のサブ窓口とする（Q5/A 確定）

1. VPS 上で Discord Bot アダプターを追加する。受信した Discord メッセージをハブ内部の**統括秘書宛て通常メッセージ**に正規化する。別 Mac 上に Discord Bot を立てず、Discord 用の PM／子セッションも作らない。
2. 受信時に Discord の投稿者 ID と受信先（サーバー／チャンネル）を確認する。**サーバー外の個人DM・グループDMを先に拒否し、秘書セッションを作成しない（Q10/A）。****サーバーチャンネルでは Q8/A のトリガー（Botへの直接メンションまたはBot本人の投稿への返信）と許可リストの両方**を満たす投稿だけ処理する。Bot自身・他Bot・Webhookの投稿は除外する。DMのメンションやBot返信も一切起動条件にしない。
3. ハブは入力元、外部メッセージ ID、投稿者、内部 `chat_id`、返信先ルートを関連付ける。返信時は秘書の `reply` をハブで検証し、**当該依頼の元窓口**にだけ返信する。秘書が受信経路を自由文で指定しただけでは他の Discord チャンネルへ送信できない。
4. **Discord Bot に個別スレッドの履歴取得、`thread_direct_send`、承認回答、セッション停止／中断、設定・ペアリングの操作を公開しない。** Discord で秘書に文章で仕事を頼み、秘書が `project_pm_send` で案件 PM に委任する通常フローは Q9/A で許可する。ただし、秘書が Discord 由来の入力に応じて低レベル `session_*` や承認・停止・設定ツールを代理実行することはハブで拒否する。
5. Discord の接続断・送信失敗・重複イベントはアダプター側で追跡する。少なくとも**受信済み／秘書への配送済み／秘書の返信済み／Discord 送信済み**を区別し、返答先が不明な場合は誤投稿せず保留／エラーにする。チャンネル単位で会話セッションを分離し、案件情報は認可済みの共通台帳から取得する（Q6/B）。

**Q5/A〜Q10/A の境界:** Discord の PM／子セッション直接操作は禁止。許可したサーバーチャンネルでは案件別の閲覧ACLを設けず共有台帳の全案件を参照可能とする。Bot起動条件は Q8/A で確定。DMはQ10/Aで**不使用と確定**し、受信・台帳参照・実作業依頼・返信の全経路で拒否する。Q9/A の実作業依頼は許可サーバーチャンネルの許可ユーザーだけを対象とする。

### 4.1.4 会話文脈の分離と案件共有台帳（Q6/B 確定）

**「統括秘書」は一つの役割／共通の指示ポリシーであり、一つの Claude Code 会話セッションではない。** VPS ハブの会話ルーターが入力元ごとに独立した対話セッションを割り当て、会話履歴が別セッションの文脈へ自動的に混入しない構成とする。

| 入力元 | 会話コンテキストの単位 | 復帰時の扱い |
| --- | --- | --- |
| WebChat | サーバーが発行し、認証利用者に紐づける `conv_id` 単位 | 同じ `conv_id` の秘書 Claude Code セッションを再開。別の WebChat 会話は独立 |
| Discord サーバー | `guild_id + channel_id` 単位（Discord のスレッドは固有のチャンネル ID で区別） | 同じチャンネルだけ同じ秘書セッションに復帰 |
| Discord DM（個人・グループ） | 対象外（Q10/A） | **セッションを新規作成せず、過去セッションも自動再開しない** |

- ハブは正規化した `context_id` を発行し、`context_id → session UUID → 会話保存先 → 返信経路` の対応を VPS に永続記録する。Discord の ID や WebChat の `conv_id` はモデルの自己申告ではなく認証された入口から導出する。再起動しても対応を復元し、**別コンテキストの UUID を誤って `--resume` しない**。
- 各コンテキストは独立した Claude Code 対話セッションおよび独立した作業ディレクトリを持つ（例: `secretary/contexts/<不透明なID>/`）。共通の役割指示・公開ツール定義は同じだが、会話トランスクリプト、プロンプト、他の Discord チャンネルの過去会話、ツール応答の全文は他の会話セッションへ自動注入しない。秘書の組み込みツールは従来どおり無効化し、共有データへのアクセスは認可済みの専用ハブツールに限定する。
- コンテキストごとにメッセージを直列処理し、複数コンテキストは設定されたセッション数上限内で並行起動できる。上限超過時は未処理を永続キューに保留するか明示的な `busy` を返し、他コンテキストへ転送して処理しない。アイドル状態のセッションは終了してよいが、次の入力で**同じ会話履歴から再開**する。
- **共有するのはハブ管理の案件台帳のみ。** `worker_id + project_id`、案件の現在状態、公開を許可した進捗要約、タスク ID・件名・状態・担当・更新時刻などの構造化データを保持する。各会話の全文、ユーザーの自由な相談内容、推論、実行ログ、画像、認証情報を共有台帳に無条件コピーしない。案件 PM による構造化した更新を受け、ハブが対象案件を検証したうえで記録する。
- 秘書は `project_status` 等の**読み取りツール**で構造化された案件の共通情報を取得する。**Q7/C:** Discord のサーバーチャンネルでは、許可した `channel_id` で認証済み投稿者から受けた質問に限り、共通台帳にある **全案件の進捗・タスク**を読める。案件単位の閲覧ACLは置かない。WebChatの既存認可は変更せず、未許可チャンネルやDMには全案件公開を適用しない。
- **依頼の帰属は会話セッションではなく `request_id` で追跡する。** 秘書が案件 PM に依頼した時点で `request_id` を生成し、PM への通知、進捗・結果、元の `context_id` と `origin_route_id` をハブに関連付ける。PM の報告は `request_id` を返し、ハブは発行元の秘書セッションにだけ通知する。同じ PM が別チャンネルから複数の依頼を受けても、最後に受けた `chat_id` へ誤配送しない。`request_id` が不明なら他の会話へ推測配送せず、未帰属の案件イベントとして保留・要確認とする。
- Discord の返信は、Bot をメンションした投稿者だけでなく**そのチャンネルの閲覧可能な全員に見える**。Q7/C ではこの共有を意図した仕様とする。**Bot がチャンネルに参加しているだけでは許可しない**。メッセージ受信時と返信・ツール実行時にハブが許可チャンネル、投稿者、明示的な公開設定を検証する。会話全文・コード・秘密情報は共有台帳には載せない。

**Q6/B と Q7/C の範囲外:** DMの入力・出力・会話作成、異なるチャンネルへの過去会話の自動要約転送、Discord からの PM／子スレッド直接操作、未許可チャンネル・DMへの全件公開。

### 4.1.5 許可したDiscordチャンネルでの全案件参照（Q7/C 確定）

- **閲覧範囲:** `discord.shared_ledger_visibility=all_allowed_channels` を明示的に設定した場合、`discord.allowed_channel_ids` に登録されたサーバーチャンネルからの認可済み質問に対して、共有台帳内の **全案件の構造化情報**（案件名／進捗概要／タスクの件名・状態・担当・更新時刻等）を返す。案件単位の閲覧ACLは使わない。追加した案件も自動的に対象になる。
- **受付の条件:** Bot 有効化、投稿者IDの受信許可、チャンネルIDの許可、および Q8/A のBotへのメンションまたはBot投稿への返信のすべての必要条件を満たす必要がある。Discordの権限やチャンネル可視性をアプリが完全に保証できるわけではなく、**チャンネルを閲覧できるDiscordメンバーには回答が公開される**。
- **公開しない情報:** WebChat・DM・他チャンネルの秘書会話全文、個々の PM／子の会話ログ、認証情報、機密ファイル本文、推論・ツールの生ログ。Q6/B で作った共有台帳を公開単位とし、モデルが自由文で他コンテキストの情報を取り出せる機能を付けない。
- **DMと変更操作:** Q10/Aにより個人DM・グループDMは受信・返信を含めて利用しない。DMからの台帳取得は拒否する。全案件の**閲覧許可**だけでは実行権限を自動付与しない。**Q9/A では別途 `discord.work_request_policy=allowed_users_via_secretary` を明示した場合に限り**、許可ユーザー全員の `project_pm_send`（秘書→案件PMへの通常委任）を許可する。停止・承認・設定や子への直接操作は含まない。
- **動的な取り消し:** チャンネルや投稿者を許可リストから外したら、その後の台帳取得と返信の**両方**を拒否する。元チャンネルが削除・権限剥奪された場合も別チャンネルへ転送しない。共有台帳の参照と返信先・結果を監査イベントに記録する。
- **OSSの安全な既定:** `discord.enabled=false`、`discord.allowed_channel_ids=[]`、`discord.shared_ledger_visibility=none`。今回のQ7/Cは本運用で明示設定して初めて適用するもので、OSS導入直後から全案件を配信する意味ではない。

### 4.1.6 Discordのメッセージ受信トリガー（Q8/A 確定）

- **反応対象:** 明示的に許可したDiscordサーバーチャンネル／スレッドにおいて、`allowed_user_ids` に登録済みの人間が投稿したメッセージが、(A) `mentions` に実際の **BotユーザーID** を含む、または (B) 同一チャンネルの**Bot本人が書いた投稿をDiscordの返信機能で参照**している場合に限り、統括秘書へ配送する。単に本文にBot名が書かれた投稿や `@everyone`、役職メンション、通常の雑談は起動条件にしない。
- **返信の検証:** 返信元の `message_reference` が示すメッセージについて、`referenced_message.author.id` または必要に応じてDiscord APIで確認した投稿者IDが現行Botと一致することを必須とする。削除・未取得・権限不足等で検証できない場合は**返信トリガーとして採用しない**。返信先が他人の投稿であっても、当該メッセージ自身にBotへの明示メンションがあれば(A)で判定する。
- **処理順序:** 「Bot投稿／Webhook除外 → チャンネル・ユーザー認可 → トリガー判定 → メッセージIDの重複排除 → 正規化・会話セッション配送」とする。**トリガー不成立の投稿は会話履歴に入れず、案件台帳へのアクセスも起動しない。** 必要最小限の拒否理由だけ記録し、雑談全文は保存しない。
- **会話と返答:** メンション／返信どちらでもQ6/Bどおり同じチャンネルの秘書セッションへ流す。Botは元の利用者メッセージへのDiscord返信として返答し、応答IDもルーティング台帳に記録する。Botの返信に利用者が返信したら、再度(B)の検証を経て継続会話となる。チャンネル外へ返信を勝手に移動させない。
- **範囲の維持:** Q8/Aは**受信契機のみ**の確定。Q7/Cで認めた共通案件台帳の閲覧範囲、Q5/Aの個別セッション操作禁止、Discord投稿者の**実行権限**はQ9/Aで別途定義する。DMはQ10/Aで不使用と確定しており、Botへのメンション・Botへの返信があっても受理しない。
- **実機確認:** Discordのイベント取得条件（必要なGateway Intents・メッセージ本文の取得可否・返信参照情報・必要時のAPI取得権限）を対象Bot設定とDiscord APIで検証する。入力テキストが取得できないときは空の指示を配送しない。

### 4.1.7 Discordの許可ユーザー全員による実作業依頼（Q9/A 確定）

- **実作業依頼の許可:** `discord.work_request_policy=allowed_users_via_secretary` を管理者が明示的に有効化した場合、`discord.allowed_user_ids` にある人間が、`discord.allowed_channel_ids` にあるサーバーチャンネル／スレッドから、Q8/Aのメンション／Bot返信を満たす投稿で、統括秘書へ調査・実装・修正・テスト等を依頼できる。**実行用の追加ユーザー許可リストは作らない。** 案件別の委任ACLも設けず、接続済みワーカーの登録済みかつPM有効な全案件を対象とする。
- **固定された指揮系統:** Discord → 当該チャンネルの秘書セッション → `project_pm_send` → 担当Macの案件PM → 必要なら子セッション。DiscordからPM・子の生セッションへ直接投稿すること、`session_create`／`session_send`／`session_stop`／`session_interrupt` 等を秘書に代理実行させること、WebChat専用の承認・設定操作は禁止する。未登録案件や任意のローカルパスも選択できない。
- **入力元認可を実行時にも適用:** 受信時にハブが採番する `ingress_id` に、検証済みの `author_id`、`guild_id`、`channel_id`、`origin_route_id`、`context_id` を紐づける。案件委任ツールの呼び出し時、ハブは認証済みブリッジセッションと**サーバーが保持する現在の依頼帰属**を照合して改めて許可を判定する。**チャンネル単位の `context_id` だけで投稿者を同定しない**。本文中・モデルが指定したIDで認可を上書きできない。
- **並行投稿と継続処理:** 同一チャンネルの複数利用者からの依頼とPM報告を `ingress_id`／`request_id` で対応づける。ツール呼び出しを特定の許可済み依頼に結び付けられない場合は委任を拒否する。会話内の入力を直列化するか同等の確実な帰属管理を行い、Claude Code Channelsの実際の呼び出し順序・再開・通知割り込み条件は実機で検証する。
- **承認と機密情報:** Q9/Aは「依頼できる権限」であり、MacのClaude Codeに無条件のツール許可を追加するものではない。既存のMac権限・承認フローを維持し、必要な人間の承認はWebChatで行う。ただし既存設定で自動許可されている操作まで毎回承認されるとは限らない。Discordへは受付・進捗・結果の**共有可能な要約**を返し、コード全文、添付ファイル、生ログ、他会話の本文や秘密値は自動返信しない。
- **変更・撤回:** 実行前に許可ユーザー／チャンネル／ポリシーが取り消された場合は新しい `project_pm_send` を拒否する。すでにMacへ配送された作業は取り消しによって自動ロールバックできないため、停止・承認・監査はWebChatで扱う。`ingress_id`、投稿者、案件、`request_id`、許可／拒否結果を最小限の監査記録に残し、Botトークンや生の指示文は監査項目に複製しない。
- **OSS既定とQ11/A:** `discord.work_request_policy=disabled` を既定とし、実運用で明示的に切り替える。DMは不使用と確定（Q10/A）。**有効化された許可依頼に対して、作業内容のリスク別の追加着手承認は設けない（Q11/A）。** 会話全文の保持期間は別途決める。

### 4.1.8 Discord DMを使用しない（Q10/A 確定）

- **対象範囲:** Discordの個人DMとグループDMを、統括秘書への会話入口・案件台帳の参照口・案件PMへの実作業依頼口・返信先の**すべてから除外する**。Q8/Aのメンション・Bot返信、Q9/Aの許可ユーザー登録ではDMを例外的に通さない。
- **入口の拒否:** Discordイベントに認証できるサーバー `guild_id` がない、またはチャネル種別がDM／グループDMなら、**チャンネル照合やメッセージ解釈より前に**破棄する。イベントID・非機微な拒否理由以外の本文を保管せず、`ingress_id`、`origin_route_id`、`context_id`、秘書セッション、作業依頼を作らない。
- **出口の拒否:** Discord返信・再送キューは**保存済みの許可サーバー `guild_id` と `channel_id` を必須**とする。DM宛てや発行元不明の返信先は拒否し、DMへフォールバックしない。BotがDiscordプラットフォームからDMイベントを受信し得ても、アプリでは処理しない。
- **設定と移行:** 未実装hub v6案の `discord.allow_dm`／`discord.context_scope` はv7案で廃止する。旧設定の `allow_dm=true` は自動的に受け入れず、移行時に管理者へエラーを示す。`false` なら廃止項目を削除できる。旧DM由来の履歴・返信ルートは隔離し、自動再開・再送を禁止する。
- **既存の確定要件は維持:** 許可サーバーチャンネル／スレッドはQ8/Aの明示メンション・Bot投稿への検証済み返信だけ処理。Q7/Cの全案件台帳参照とQ9/AのPM実作業依頼を維持。MacワーカーはDiscordの詳細を知らず、WebChatの直接介入権限も変更しない。

**Q10/Aの受入試験:** 許可ユーザーがDMでメンション、Bot返信、作業依頼、進捗確認を送っても**秘書起動・台帳アクセス・Macへの命令・Bot返信が0件**であること。再起動・古いキュー・設定移行を経てもDMへ配送しないこと。サーバーチャンネル／スレッドの既存機能は正常動作すること。

### 4.1.9 Discord実作業依頼は追加の着手承認を要求しない（Q11/A 確定）

- **開始条件:** Q8/Aのメンション／Bot返信、Q9/Aの許可ユーザー・許可サーバーチャンネル・`discord.work_request_policy=allowed_users_via_secretary`、登録済みPM有効案件への委任条件をすべて満たすなら、ハブは `project_pm_send` を受け、**独自の着手承認を挟まずに** `pm_send` へ進む。投稿の受付・ツール呼び出し時の認可再確認（`ingress_id` 等）は省略しない。
- **高影響操作:** 本番デプロイ、大量ファイル削除、外部送信などの依頼内容を理由として、Hannigan独自の「作業開始待ち／WebChat承認待ち」状態を追加しない。リスク判定AIが自動で人間承認を発行する新規機構も設けない。これは作業を無条件許可するという意味ではない。
- **既存ツール承認:** Mac上の `role=pm` および `role=task` の `permission_mode`、`allowed_tools`、既存フックやmacOS権限を変更しない。Claude Codeがツール承認を要求した場合のみ従来の permission relay → WebChat 承認を使う。CUアプリ承認や作業フォルダ信頼確認など既存の端末確認も従来どおり扱う。Discordの投稿者には承認回答権を与えない。
- **自動許可される操作:** Claude Code側で既に許可済みのツールは承認画面を経ずに実行され得る。**Hanniganがリスク別に追加承認を掛けないことにより、本番反映等にも確認が入る保証はない。** 新たに `bypassPermissions` 相当へ切り替えたり、Hannigan側が既存承認を自動回答したりはしない。
- **実行可能性:** 即時着手承認が不要でも、Macのオフライン、`max_sessions` 超過、キュー、起動遅延、Claude Codeの承認待ちによって実行は遅延・失敗し得る。Discord上の「依頼受付」「PM配送」「実行中」「承認待ち」「完了」を区別し、受付だけで実行・完了を宣言しない。
- **既存境界は不変:** Discordの `session_*`、`thread_direct_send`、承認回答、停止、設定変更へのアクセスは禁止したまま。DM拒否、返信元の検証、共有台帳の情報制限、`request_id` の経路追跡も維持する。

**本項は設計決定であり実装・動作保証ではない。** 対象Claude Code版における自動許可／承認要求／CU端末確認の経路をMac実機で検証する。

### 4.1.10 Macオフライン時の期限付き依頼保留（Q12/C 確定）

**適用対象:** `project_pm_send → pm_send`（WebChat・Discordの秘書経由の通常案件依頼）と、認証済みWebChatからの `thread_direct_send`（PM／子スレッドへの直接追加指示）。後者もQ4/Bの直接指示であり、統括秘書に文章を再解釈させない。**承認回答、CU端末の選択キー、停止・中断、設定変更、ペアリングは保留しない**。これらは時限性が高いためオフライン時に失敗する。

1. **受付と保存:** ハブは元の認可・チャンネル／セッション所属を確認してから、`request_id`（秘書経由）または `message_id`（直接指示）をキーに `hub/offline-requests.jsonl` へ一回だけ永続登録する。記録には送信元コンテキスト／元返信ルート・投稿者・対象ワーカー／案件／セッション・指示本文（制限アクセス領域）・受付時刻・`expires_at`・配送状態を持たせる。**ディスコードやWebChatの生メッセージを共有案件台帳へ複製しない**。
2. **有効期限（Q13/C確定）:** `expires_at = VPS の受付時刻 + offline_queue.ttl_minutes`。**既定値は1,440分（24時間）**で、受付時刻はVPSのUTCを正とする。利用者の文面・Macの自己申告・再試行・ハブ再起動では期限を延長しない。`ttl_minutes` 省略時は1,440を適用し、明示的な `null`／0／負数／不正値は設定エラーとする。運用者が正の整数へ設定変更できるが、既存保留依頼の `expires_at` は書き換えない。`expires_at` と同時刻以降は未配送として失効する。
3. **期限内の復帰:** 再接続したMacの認証と `inventory` を確認し、配送直前に発行元の現在の認可・案件／PM有効状態・直接指定したセッションと親PMの同一性を再検査する。期限切れ、認可取消、対象消滅なら**自動配送しない**。子の指定セッションが存在しない場合に別のセッションやPMへ自動転送しない。
4. **送信の有効期限:** ハブでの送信直前と、Macデーモンの**チャネル流し込み直前**に `expires_at` を確認する。Macが接続しただけでは配送成功としない。PMの再開・ブリッジ準備が期限に間に合わなければ失効する。期限内にチャネルへ配送された仕事は、期限経過だけでは実行中のClaude Codeを停止しない（TTLは**未配送指示の有効期間**であり、作業の完了期限ではない）。
5. **冪等性と障害:** ハブ側の依頼IDとMac側の永続受信台帳を照合し、再接続・HTTPリトライ・WSS再送で同じ仕事を二重に流し込まない。配送確定前後に通信が切れ、流し込んだか確定できない場合は `delivery_unknown` として**無条件で自動再実行せず**WebChatで確認を求める。Claude内部での厳密な1回処理まで保証しない。
6. **WebChatからの子への直接指示:** 復帰後にMacが `thread_direct_send` を受理したとき、子への指示と担当PMへの**事実通知**を単一ジャーナルで登録し、既存のQ4/Bの二系統配送を開始する。VPS保留中にPM通知だけを先行送信しない。
7. **期限切れ・中止:** 未配送の保留依頼は `expired` にし、再接続後も配送しない。元のWebChat会話または元のDiscord投稿への通知を試み、Discordでは送信直前にQ7〜Q10の認可を再検査する。返信先が失効／許可取消なら別チャンネルやDMへ送らず、WebChat管理画面内の失効履歴・通知で確認できるようにする。WebChatから保留中の依頼を取り消せるが、配送済みの作業が巻き戻るとは表示しない。
8. **承認との区別:** オフライン待ちは `pending_offline`、ツールの承認待ちは `awaiting_approval`。Q11/Aに反して独自の着手承認を追加しない。`pending_offline` の受付は「実行開始」「作業完了」ではない。

**Q14/Bで確定:** 同一Macに複数の保留依頼がある場合はVPS受付順で配送し、ワーカーは独立した作業を既存の `max_sessions` 制限内で並列進行できる。ただしCUはMacにつき1セッションの排他制御、ファイル書込は競合防止の強制機構を必須とする（4.1.11）。Q15/Bでは共有フォルダ＋単一ライター方式、Q16/Aでは作業完了と書込停止の安全確認後に書込権を自動解放すると確定。異常時の復旧方針はQ17/B（安全な自動再検証・確認不能なら書込権保持とWebChat通知・自動強制終了禁止）に確定した。巨大な添付ファイルの取扱いは未決定。配送キューは上限超過で黙って捨てず `queue_full` を返す。

### 4.1.11 復帰後のFIFO配送と安全な並列作業（Q14/B 確定）

1. **順序の定義:** VPSはワーカー単位に `accepted_at`（Q12/Cで保存したUTC受付時刻）昇順、同時刻なら不変の `operation_id` 昇順で並べる。再接続したMacの `hello`・`inventory` 同期後に古い依頼から `command` を送る。新しいオンライン依頼が復帰前の保留を追い越さないよう、ワーカー単位の送信順を統制する。失効・取消・認可失効済みの依頼は配送対象から除外して状態を記録する。
2. **順序と並列性の両立:** 先行依頼がMacデーモンの永続受理台帳で**受理済み**になったら次の依頼を送ってよい。`worker_queued`／`resource_wait` は受理済みであっても**Claude Codeへ投入済みではない**。ワーカーは既存の `max_sessions` 内で、互いに競合しない案件／作業を並列実行できる。**FIFOはVPS→Macの配送・受理順を保証するもので、リソース待ち後のClaude投入順・着手順・完了順を保証しない。**同一PMセッションへの通知自体は受理順を維持する。
3. **CU排他:** 同一Macでは純正CU利用を必要とするセッションに対し、一つの所有者だけを持つ排他管理を導入する。所有中の別CU要求は `resource_wait(reason=cu_busy)` として待機させ、無断で別セッションへ変更しない。CUのセッション単位の占有可能性を踏まえ、**ツール呼び出しが一度終わっただけでは解放しない**。所有セッションの終了と実際の解放を確認後に次へ付与する。外部から強制可能な排他／CU呼出し制限が成立するまではCU並列起動を禁止して縮退運用する。
4. **ファイル競合対策:** オフライン復帰分だけでなく、既に稼働中のPM・子やオンラインで受けた直接指示・PMからの `task_send` を含む**書込可能な全Claude Codeセッション**を対象にし、同じ実体作業領域（シンボリックリンクや別名パスも正規化）の同時書込を禁止する。Q15/Bにより同一作業フォルダを共有し、当該領域の書込可能セッションを直列化する運用とし、別の実体作業領域への書込や**技術的に読取専用と制限できた**調査作業だけを並列候補とする。自然言語の「同じファイルを触らない」指示、PMの判断、`max_sessions` 上限だけでは排他の実装とみなさない。
5. **期限と再接続:** `expires_at` はQ13/Cの受付から24時間のまま。CUや編集領域のリソース待ちでMacが受理済みでも、**Claude Codeへのチャネル投入前**に期限が来たら失効・未実行通知を行う。配送試行・ロック待ち・ハブ／Mac再起動で期限を延長しない。すでに投入済みの実作業は期限のみで中断しない。二重配送を防ぐQ12の `request_id`／`message_id` は引き継ぐ。
6. **可視化:** WebChatには `pending_offline`（VPS待ち）、`worker_queued`（Mac受理）、`resource_wait`（CU／編集領域待ち）、`delivered`（チャネル投入）、`working`、`completed`、`expired` を混同せず表示する。これらは新しい着手承認ではなく安全な資源調整であり、Q11/Aの方針を変更しない。

**実装上の境界:** 特定の Claude Code セッションが実際に使用するファイルパスやCU開始を、既存のチャネル通知・tmux画面だけでは確実に制御できない。OSレベルの隔離、ツール実行時の制御、CU用の利用経路制限等を対象版で検証し、強制できない経路は許可しない。**Q14/Bは実行制御の必須要件を定めたものであり、現在の実装が排他を保証するという意味ではない。**

### 4.1.12 同じ作業フォルダの共有と単一ライター制御（Q15/B 確定）

**採用する方式:** 案件PMと子のClaude Codeは、同じMacの `projects[].path` で指定された**同一の実体作業フォルダ**を使用する。Q15ではGit worktree・子ごとの専用ブランチ・作業コピーによる隔離を採用しない。非Git案件も同じ方式で扱う。PMが子の変更内容をそのまま共有フォルダから確認できる一方、同じ作業領域に**書込可能なセッションは同時に最大1つ**とする。

1. **排他の対象:** `role=pm` と `role=task` の両方。秘書からの `pm_send`、WebChatの `thread_direct_send`、PM自身の `task_send`／直接編集、復帰後の保留依頼、既に起動したセッションからのツール呼出しも例外にしない。複数の `project_id` が同一・親子・シンボリックリンク経由の重複パスを指す場合も競合とする。別の非重複フォルダは、Q14のCU制限と `max_sessions` を満たせば並列実行可能。
2. **単一ライター:** Macデーモンが実体作業領域に対する書込枠の所有セッションを管理し、所有者以外にはその領域を**技術的に書込不可**とする。PMが書込中なら子の書込要求は `resource_wait(reason=workspace_busy)` にする。子が書込中ならPM自身の書込も同様に待つ。書込枠はセッション・実体パス・命令IDに紐づけて永続記録し、再起動時に再照合する。
3. **読取並列:** 書込枠を持たないセッションも、ファイルシステム・組み込みツール・Bash・バックグラウンドプロセスなど**すべての経路で読取専用が強制できる**場合だけ読み取り調査を並列実行してよい。Claudeへの「編集禁止」の文章やアプリの `max_sessions` だけでは保証とみなさない。強制できない場合は、その作業領域で同時稼働する書込可能プロセス／セッションを1つに限定する保守的な直列運用へ縮退する。
4. **PMと子の引継ぎ:** PMが子へ編集を委任しても自動的に二重ライターとはならない。子に書込枠を渡す前にPM側の書込可能経路・実行中プロセスを安全に停止または読取専用化できたことを確認する。子の作業後にPMがレビュー・追加修正する場合も同じ制御を通す。**Q16/Aにより、作業完了と書込停止・権限剥奪を検証できたら、セッションを維持したまま自動返却する。**確認不能なら `resource_unknown` として解放しない（4.1.13）。
5. **期限と表示:** Q13/Cの24時間TTLは、保留・受理後でも**Claude Codeに指示を投入する前**の資源待機に適用し続ける。投入済み作業はTTL到来だけで中断しない。WebChatには `resource_wait(reason=workspace_busy)`、対象案件、可能なら現在の所有セッションを表示し、Discordの元依頼には勝手な完了報告をしない。資源待ちを新たな人間の着手承認と解釈しない（Q11/A維持）。
6. **既存ワークツリーと外部書込:** Hanniganは新しいworktreeを作らない。既存の別worktreeや任意の作業フォルダ外へClaude Codeが書き込める場合には、排他対象外への書込や別経路からの迂回が可能なので、OS／ツール権限による封じ込めを検証する。競合判定と強制が成立しない状態では安全な並列編集を実装済みと扱わない。

**実装の位置づけ:** Q15/Bで方式は確定したが、macOS上のClaude Codeの組み込みEdit/Write/Bashと子プロセスを含めて「所有者以外は本当に書けない」を保証する機構は未実装・未検証。ファイルロック台帳のみでは強制力が不足するため、技術検証できない場合は書込可能セッションを直列起動・停止する。Q14/Bの「競合しない作業は並列実行」は、同じ作業領域で無条件に複数ライターを認めるものではない。

### 4.1.13 書込権の作業完了後自動解放（Q16/A 確定）

**決定:** Q15/Bの単一ライターは、Claude Codeの**セッション終了まで占有する方式にしない**。PM／子セッションは会話履歴とセッションIDを維持し、**当該作業単位の完了および書込停止・旧所有者の書込不能化を検証した後**、Macデーモンが書込枠を自動解放する。ユーザーによる都度のWebChat承認や明示解放は要件としない。新しい書込作業が来たら、同じ継続セッションでも再取得する。

1. **所有単位:** 書込枠は `normalized_workspace + session_key + operation_id` に結びつく。Discord／WebChat→案件PMの `request_id`、WebChat→PM／子の `message_id`、PM→子のローカル作業IDなどから安定した `operation_id` をMac側で採番・永続化する。会話セッション単位で永久保持しない。同一セッション内で重なる書込作業は、書込開始を直列化する。
2. **完了候補と確定の区別:** Claudeの `reply`、tmuxの `ready`、進捗の「完了」は作業完了の**候補信号**でしかない。該当操作のツール呼び出し・シェル処理・バックグラウンド子プロセス・保留書込が残っていないことを確認するまで解放しない。進捗通知や部分回答でも解放しない。
3. **実際の解放手順:** `held → release_pending` を永続記録し、旧所有者に対して**新たな書込権をOS／ツール実行境界で剥奪**する。実行中・非同期の書込主体が残っていないことと書込不能化の強制力を確認し、資源台帳を `released` に更新してから次の待機者へ付与する。旧セッションが生きているだけで書込可能になってはならない。資源台帳の世代番号等で古い所有者の遅延書込・復旧時の再取得競合を防ぐ。
4. **不明時:** 書込停止、子プロセス、権限剥奪、保存済み所有情報のどれか一つでも確認不能なら `resource_unknown` として**自動解放せず**新規ライターを止める。デーモン再起動・ハブ切断・Claudeの `reply` のみを解放証拠としない。安全確認方法の実装・Mac実機検証が必要。
5. **待機依頼への引継ぎ:** 解放完了後、同じ実体作業領域の待機依頼から、失効・取消・認可・対象セッションを再検証したものだけ次の所有者候補にする。Q14/BのFIFOは**VPS→Macの受理順**であり、書込権の待機者間の優先順位をこの回答で新規確定したものではない。ブリッジ未投入の依頼にはQ13/Cの24時間TTLを適用し続ける。
6. **CUとは独立:** この自動解放は**ファイル書込権だけ**に適用する。純正Computer Useのセッション単位ロックはQ14/Bの「CU側で実際の解放を確認する」条件を維持し、作業完了だけで解放したことにしない。

**成立性の留保:** 長寿命のClaude CodeセッションからBash・ツール・バックグラウンドプロセスを含む全書込経路の権限を安全に剥奪できるかは未検証。成立しない場合は**同一フォルダで複数の書込可能セッションを並走させない**。必要ならプロセスを安全に休止／終了して履歴から再開する縮退案を検証するが、実証前に「セッションを生かしたまま安全に自動解放できる」とは扱わない。

### 4.1.14 書込権所有者の異常時に安全な自動復旧を試みる（Q17/B 確定）

**決定:** 共有フォルダの書込権所有者である案件PM／子セッションに異常停止、ハング、状態不整合が生じたら、Macデーモンは**安全確認のための自動復旧（状態の再照合・再接続・再検証）を試みる**。書込停止と権限剥奪が客観的に確認できた場合に限り、Q16/Aの解放処理を再開できる。**安全性が確認できなければ書込権を保持したまま `resource_unknown` に置き、WebChatへ要確認通知を出す。自動強制終了・強制ロック解除は行わない。**

1. **異常の検知:** Claude Code／tmuxの予期せぬ終了、応答途絶・ハング、ブリッジ切断、デーモン／Macの再起動、`release_pending` 中の不整合、子プロセスや権限制御の確認失敗などを契機とする。ハングと断定できない単なる遅延だけで所有権を奪わない。
2. **許可する自動処理:** 保存済みの `resource_id`・`session_key`・`operation_id`・`lease_epoch` と tmux／Claude Code／子プロセス・実体作業パスを突き合わせる。生存している既存のブリッジには再接続してよい。ツール処理・派生プロセス・バックグラウンドジョブとOS／ツールの書込権境界を再検証し、未確定の所有者へ新たな書込権を付与しない。異常タスク本文を自動再投入しない。
3. **自動復旧成功の条件:** 旧所有者が書込可能な経路を持たず、継続中の書込主体が存在しないことを**強制境界とプロセス証跡から確認**し、所有世代との整合を永続化できた場合に限り `released` を確定する。作業が実際に継続中で安全な管理状態に戻せた場合は `held` を維持し、他の所有者へ渡さない。プロセスが見えない、一定時間無応答、端末に入力欄がある、というだけでは安全の証明にならない。
4. **失敗時はfail-closed:** 上記のいずれかが曖昧なら `resource_unknown`／必要に応じ `release_pending` を維持し、同じ実体作業領域への新たな書込を拒否・待機させる。自動 `Esc`、`/exit`、kill、tmux破棄、Mac再起動、強制的な権限上書き、資源台帳の削除は行わない。手動操作の許可範囲はQ18以降の判断事項で、Q17/Bだけで拡大しない。
5. **通知と復旧記録:** `resource_lease_state` で資源・所有世代・異常理由・再照合結果を耐久イベントとしてVPSへ送る。確認不能ならWebChatの管理画面に要確認の通知を永続表示し、対象Mac／案件／セッションと「自動復旧不可」を分かるようにする。SSE切断／ハブ再起動後も未解決状態を再表示する。Discordの通常会話や共有案件台帳へ内部プロセス詳細・パス・機密値を流さない。
6. **既存の期限・並列ルール:** 待機中の未投入指示はQ13/Cの24時間TTLで失効し、既にClaudeに配送した指示は期限のみで中断しない。関係のない作業領域はQ14/Bの範囲で継続できる。純正CUの所有ロックは別資源であり、書込権の検査でCUの占有まで解除しない。

**検証上の留保:** macOS上でセッション継続中の全書込経路を確実に制限・検証する実装は未完了。Q17/Bは検証できない状況で勝手に解放する許可ではなく、**未確認状態を安全に保持したまま、復旧可能性を自動調査する設計決定**である。

### 4.2 スレッド（セッション）の作成と再開

Channels からは新しいスレッドを作れないため、常駐プログラムがプロセスの起動で代替する。

- 秘書作成: ハブが `context_id` を検証して該当会話の秘書 UUID を検索し、未作成ならコンテキスト専用フォルダで `role=secretary` の対話セッションを起動。複数会話に同じ UUID を割り当てない
- PM 作成: `pm_send` が担当案件の PM を確認し、未作成なら案件フォルダで `role=pm` の Claude Code 対話セッションを起動。同じ案件に二重作成しない
- 作業作成: 案件 PM が委任を選んだ場合のみ、`task_create` により同じ案件フォルダで `role=task` の独立セッションを起動する。軽量作業では子を作成しない。通常の `session_create` も基本処理として保持
- CLI 起動: `claude --session-id <UUID> --mcp-config <ブリッジ設定> --dangerously-load-development-channels server:hannigan` を tmux 内で起動。履歴はそのフォルダに紐づく（詳細は [02](02-worker-daemon.md)）
- 再開: 同じフォルダで `claude --resume <UUID>`。会話履歴とチャネル登録は維持される（検証 T10、Phase 2 の一巡試験）
- 終了: tmux へ `/exit` を送る

### 4.3 承認と停止

| 場面 | 経路 | 備考 |
| --- | --- | --- |
| 通常ツール（Bash、Write、返信ツールなど）の承認 | ワーカーチャネルの permission relay → 常駐プログラム → ハブ → WebChat | 検証 T03/T04/T08 で成立 |
| CU のアプリ承認、開発用チャネルの起動時警告、フォルダの信頼確認 | 端末ダイアログのみ。常駐プログラムが tmux 画面を読み取って WebChat に表示し、選択キーを送る | Channels の機能ではなく端末操作の代行 |
| 実行中の停止 | 常駐プログラムが tmux へ Esc を送る | 検証 T09。停止後は画面で実状態を確認する |

CU のアプリ承認はセッション起動時に 1 回で、同じアプリなら以後は不要（検証 T05〜T09）。
使うアプリを固定し、セッションを落とさずに保てば、日常の承認はほぼ発生しない。

## 5. 秘書 Claude から見えるツール

確定版は [03 の 6 章](03-hub-worker-protocol.md)。

| ツール | 引数 | 常駐プログラム側の動き |
| --- | --- | --- |
| `workers_status` | なし | ワーカー・案件別 PM・子作業セッションの一覧と状態 |
| `project_pm_send` | worker, project, text, chat_id? | ハブで `ingress_id`・発行元コンテキストを認可し `request_id` を発行。Q9/Aでは許可Discordユーザーの登録案件PMへの委任を許可。作業セッションへは直接送らない |
| `project_status` | worker?, project? | 認可済み共有台帳から案件概要・進捗・タスク情報を取得。他の会話全文は返さない |
| `session_create` | worker, project, name | デーモンの従来の作業セッション作成機構。通常の依頼では PM が呼び出すローカル `task_create` を優先 |
| `session_resume` | worker, session_id | 同じフォルダで `--resume` |
| `session_send` | worker, session_id, text | セッションのチャネルへ流し込む |
| `session_stop` | worker, session_id | `/exit` を送る |
| `session_interrupt` | worker, session_id | Esc を送る |
| `reply` | chat_id, text, in_reply_to | 呼び出し元の秘書セッション UUID と `chat_id`／`request_id` の発行元コンテキストが一致する場合だけ、WebChat または Discord の元の会話へ返信 |

Discord起点の秘書ツールでは `project_pm_send` のみを通常委任に認め、`session_*` の代理呼び出しはハブで拒否する（Q9/A）。WebChat の直接投稿は秘書向け MCP ツールではなく、ハブの `POST /api/thread/send` → ワーカーの `thread_direct_send` で扱う。PM／子の送信先は明示指定し、子への投稿時は PM 通知を自動で行う。

命令は固定の種類にし、起動や停止に Claude の判断を挟まない。案件 PM の指示は権限付きのローカルツール呼び出しでデーモンが実行する。PM には**自分の案件の子セッションだけ**を制御させ、他案件の操作はデーモン側で拒否する。

## 6. 設定の方針

- 設定ファイルを唯一の正とし、設定画面はそれを読み書きする道具にする。ファイル直編集でも動く
- 秘密情報（WebChat トークン、Discord Bot トークン、ワーカーの接続鍵）は設定ファイルと分け、権限 600 のファイル（VPS を含む）か対応 OS のキーチェーンに置く
- Claude Code 側の準備（MCP/Channels 設定・起動フラグ）は VPS 側秘書と Mac 側ワーカーの両方で行う。CU の有効化、macOS の権限付与は Mac ワーカーだけが対象。
  導入 CLI が準備し、設定画面は「準備 OK／権限不足」の状態を表示する
- ワーカーの追加はペアリング方式（ハブが一時コードを発行し、作業 Mac で `pair <code>`）
- ワーカーの役割説明文はハブが各秘書セッションの `instructions` に組み込む。接続時に Claude へ渡されるため、変更後はセッション再接続が必要
- Q6/B では複数秘書セッションの定義・帰属・復元と、共有案件台帳のアクセス制御を VPS に追加。案件の情報を会話トランスクリプトにコピーする形で共通化しない

PM の有効化、起動条件、役割別ツール権限、`execution_policy=hybrid`（Q3/B の既定）、WebChat の直接スレッド投稿と履歴表示、Discord の受信・投稿許可、Q8/Aの起動トリガーとQ9/Aの作業依頼ポリシー、Q12/Cの期限付きオフライン依頼キュー、および秘書コンテキスト分離／案件台帳の設定は [01 設定スキーマ](01-config-schema.md) で定義する。スキーマ変更と対応する移行処理の実装が必要。

## 7. アカウントと運用上の注意

- VPS の秘書 Claude Code と各 Mac の作業 Claude Code は、それぞれ実行環境ごとに認証・ログインが必要。Channels はアカウントを区別しない
- 同じアカウントを VPS と複数 Mac で使う場合、利用量の上限を共有する
- Team / Enterprise のアカウントは、管理者が組織設定で Channels を有効にする必要がある
- 仕事の作業内容・個別スレッドの発言や表示用の活動ログは VPS に転送・保存され得る（直接介入は秘書の再解釈を通さない）。Discord の会話は Discord 側にも保存され、許可されたチャンネルの参加者に閲覧され得る。アクセス制御・保存期間・機密情報のマスキング・委託先やデータの取扱いを先に確認する
- VPS はサービス自動起動とプロセス監視、**複数**秘書セッションの復元、会話ごとの履歴隔離、共有案件台帳とログの保全を行う。Mac はスリープ対策・停電復旧・GUI 権限・画面ロック時の CU 実行可否を別途確認する
- 想定外（新アプリの承認、セッション消失）に備え、SSH + tmux attach の安全網を VPS と各 Mac に用意する

## 8. 既知の制約（2026-10-12 時点）

- Channels は研究プレビュー。自作チャネルは `--dangerously-load-development-channels` が必要で、フラグ名と仕様は変更の可能性がある
- 公式の許可リストへの掲載は Anthropic のパートナー窓口経由。Team / Enterprise は管理者が自組織のリストに追加できる
- 1 台の Mac で CU を使えるセッションは同時に 1 つ（セッション終了までロック）。Q14/Bではデーモンで排他調整する設計を追加するが、純正CUの予約／開放を外側から確実に強制・確認する方法は未実測
- Mac の純正 CU は非対話モード `-p` では使えない。ワーカーは対話セッションで起動する。なお Channels の `-p` 可否については旧設計の記載と現行公式ドキュメントに差があるため、Claude Code の対象版で別途検証する
- 日本語 macOS では CU の `request_access` にアプリの表示名が通らない場合があり、bundle ID（`com.apple.TextEdit` など）で指定する

## 10. 次の作業

順序は [ROADMAP](../ROADMAP.md) で固定した。ローカル実地テスト → VPS → Discord の順に進め、前の段階が本物の Claude で成立するまで次の配置に移らない。

1. **Phase 3 ローカル実地テスト**: ハブ・秘書・WebChat を手元の Mac で起動し、同じ Mac（任意で LAN 内の 2 台目）のワーカーに対して、案件 PM の起動／再開、軽量作業の直接実行、長時間／CU 作業の子への委任、PM による報告集約、案件越境の拒否（Q2/Q3）、WebChat からの PM／子直接投稿と子介入→PM 通知と履歴表示（Q4）、会話ごとの秘書セッションと共有台帳と `request_id` による復路（Q6）、ワーカー停止中の 24 時間保留と復帰後の FIFO 配送と失効通知（Q12〜Q14）、同じ作業フォルダの書込直列化（Q15）を通しで検証する。書込権の自動解放と異常時の自動再検証（Q16/Q17）は、全書込経路をセッション維持のまま封じられるかの検証スパイクを先に行い、その結果で方式を確定する。
2. **Phase 4 VPS**: Linux VPS 上での Claude Code 常駐（ログイン、tmux、開発用チャネルの承認、会話別セッションの復元）を先に検証し、ハブと秘書を VPS に移す。ペアリング、`wss://` による Mac からの接続、承認の集約画面、別ネットワーク試験、VPS 再起動時のキュー復元を行う。
3. **Phase 7 Discord**: 許可リスト認可、メンション／Bot 返信だけへの反応（Q8）、秘書経由の PM 委任（Q9）、代理 `session_*` の禁止、返信ルーティング、重複排除、DM イベントの入口拒否と DM 宛ての再送禁止（Q10）、追加の着手承認なし（Q11）を受入試験する。

**Q1〜Q17 は設計決定であり、新機能の動作実証ではない。** 各フェーズの出口条件は ROADMAP に置く。

## 11. ヒアリング決定記録（2026-10-15〜16）

- **確定 Q1 / A:** ハブ、WebChat 配信、統括秘書 Claude Code は VPS 上で稼働する。仕事用・私用の Mac はワーカーとする。
- **確定した設計上の境界:** 純正 CU は Mac ワーカーの Claude Code 上のみ。秘書は VPS で管理・振り分けを担当する。
- **確定 Q2 / B:** 案件別 PM Claude Code は各案件を保持する Mac 上で稼働する。VPS の統括秘書から PM へ指示し、PM はローカルの作業セッション群を束ねて結果を返す。
- **今回の実装用暫定規約:** PM は `(worker_id, project_id)` ごとに一意の `role=pm` セッションとし、作業セッションは `role=task` として識別する。起動は原則オンデマンドとする（常時自動起動は設定で変更可能）。
- **確定 Q3 / B:** PM は軽量な調査・小規模修正を直接実行し、長時間・並列・CU 作業は原則子セッションに委任する。PM が両経路の結果を統括し、VPS の統括秘書へ報告する。数値しきい値は設けない。
- **確定 Q4 / B:** WebChat で案件 PM と子セッションの両方のスレッドを閲覧し、それぞれへ直接投稿できる。子へ直接送った指示は担当 PM に通知し、PM の集約報告経路を維持する。ターミナルの直接キー操作は含めない。
- **確定 Q5 / A:** Discord は既存の VPS 統括秘書への会話用サブ窓口。PM／子セッションの閲覧・直接介入、承認・設定操作の窓口にはせず、Discord の入力元に返信を返す。
- **確定 Q6 / B:** WebChat の `conv_id`、許可Discordサーバーチャンネル／スレッドごとに秘書 Claude Code の会話セッションを分離。案件・進捗・タスクだけを VPS の共通台帳で管理し、権限付きで参照する。PM 報告は `request_id` で発行元秘書セッションへ返す。
- **確定 Q7 / C:** 明示的に許可したDiscordサーバーチャンネルでは共通台帳の全案件を閲覧可能にする。案件別閲覧ACLは不要だが、許可チャンネル・許可投稿者・公開モードを検査する。
- **確定 Q8 / A:** 許可DiscordサーバーチャンネルではBotへの直接メンションまたはBot本人が投稿したメッセージへの返信に限り統括秘書を呼び出す。Botの自己投稿、他Bot、通常の会話は無視する。
- **確定 Q9 / A:** `allowed_user_ids` の許可利用者全員が、許可サーバーチャンネルでBot呼び出し条件を満たせば、全登録案件PMへの作業委任を統括秘書経由で依頼できる。別の実行者リストや案件別ACLは設けないが、承認・停止・子への直接介入はWebChat専用。
- **確定 Q10 / A:** Discord DM（個人・グループ）は使用しない。受信・返信・会話セッション・台帳・PM委任の全経路で拒否する。
- **確定 Q11 / A:** Discordで認可された実作業依頼は追加の着手承認なしにPMへ配送。既存Claude Codeツール承認・CU端末承認は変えず、危険操作が自動許可され得ることを明示する。
- **確定 Q12 / C:** Macオフライン時の案件PM依頼とWebChat直接スレッド指示はVPSで期限付き保存。期限内にMac・Claudeの配送経路が復帰し再認可を通過すれば自動配送、期限切れは未実行通知。既存の承認・停止コマンドはキューに入れない。
- **確定 Q13 / C:** オフライン保留の既定TTLは24時間（1,440分）。受付時刻から計算し、期限到来後の未配送指示は実行しない。OSS初期状態のキュー無効は維持。
- **確定 Q14 / B:** Mac復帰後の保留指示は受付順に配送し、独立した作業は並列実行可能とする。同じMacの純正CUは1セッションのみ、同じ実体作業領域の書込競合は技術的に防止する。
- **確定 Q15 / B:** 案件PMと子は同じ実体フォルダを共有。書込可能なセッションは1つのみ、実行制御による強制が前提。
- **確定 Q16 / A:** 作業完了後、書込停止と旧所有者の書込不能化を確認できた時点で書込権だけを自動解放する。セッションの会話履歴は維持し、再編集時には書込枠を再取得する。
- **確定 Q17 / B:** 異常時は書込リース・プロセス・権限境界を安全に自動再検証し、確認不能なら `resource_unknown` に保持してWebChatへ通知する。自動強制終了・無検証の解放は禁止。
- **未決定:** 人間による異常時の遠隔復旧操作範囲（Q18）、複数 Mac にまたがる同一案件、本番認証と利用者権限、ログの保存期間。
- **実装前の確認:** VPS の対象 OS・Claude Code 版で Channels 対話セッション常駐、tmux 復元、ブリッジ接続を実測する。Mac 側のネイティブ会話ログからリアルタイムにどこまで発言・実行要約を抽出できるかを実測する。VPS ホストでの純正 CU は求めない。

## 12. Q7/C の追加受入条件（許可チャンネルの全案件参照）

1. Bot・チャンネル・投稿者が許可され、公開モードが `all_allowed_channels` のとき、`project_status` から登録済み全案件の構造化状況が返る。新しい案件の追加後も案件別ACL更新なしに表示される。
2. 未許可チャンネル、未許可投稿者、未設定／`none`、DMからの同じ質問には、共有台帳のデータを返さない。Discord Botの参加だけでは許可されない。
3. 許可チャンネルでも、別チャンネル／DM／WebChatの会話全文やPM・子セッションの生ログが `project_status` に混入しない。
4. 取得開始後、返信前に許可チャンネルが解除された場合、返信を中止し、元の会話への保留／エラーとして扱う。別のチャンネルへフォールバックしない。
5. 台帳の全件閲覧権を持っていても、未認可のセッション作成・変更・停止が許可されない。Q5/A の個別スレッド直接操作禁止は維持する。

## 13. Q8/A の追加受入条件（メンション／Botへの返信で起動）

1. 許可したサーバーチャンネルの許可投稿者がBotを**直接メンション**すると、元メッセージが同一チャンネル専用の秘書セッションに1回だけ届き、元投稿へのDiscord返信が返る。
2. 同じ許可チャンネルで**Bot本人の投稿へ返信**すると、メンションなしでも秘書セッションに届く。返信先が他人の投稿、参照メッセージ削除／取得不能の場合は返信だけでは起動しない。
3. 通常の雑談、本文にBot名があるだけの投稿、役職メンション、`@everyone`、Bot／Webhookの投稿、非許可ユーザー・チャンネルの投稿は無視する。無視した内容を秘書セッションの会話ログ・案件台帳へコピーしない。
4. Discordスレッドは固有 `channel_id` を明示許可した場合だけ有効とする。親の許可を継承せず、Q6/Bの会話分離を維持する。
5. Bot返信→利用者の再返信で同一コンテキストの会話が続くが、Discordイベントの再受信や接続断後のリトライで指示を二重投入しない。Discord送信成功とClaudeの処理／作業完了は区別する。
6. Discord側の参照情報が無い・権限不足・本文取得不可の場合は処理を安全に中止する。Gateway Intents・Bot権限・返信参照の実機試験が完了するまで動作実証済みとはしない。
7. DMの権限を暗黙に拡張しない。全案件の**閲覧**（Q7/C）とPMへの**実作業委任**（Q9/A）は、それぞれ明示設定を要する別の認可とする。

## 14. Q9/A の追加受入条件（許可ユーザー全員の秘書経由PM委任）

1. 許可ユーザー＋許可サーバーチャンネル＋Q8/Aトリガー＋`work_request_policy=allowed_users_via_secretary` の組み合わせで、登録済みの全PM有効案件へ `project_pm_send` が許可され、担当MacのPMが依頼を受ける。別の作業者用リストや案件別ACLを要求しない。
2. 受信許可・全件台帳閲覧だけを設定した場合や `work_request_policy=disabled` の場合は、`project_pm_send` を実行できない。非許可ユーザー・チャンネル、DM、Bot／Webhook投稿も実作業を起動しない。
3. 秘書がDiscord由来の会話を理由に低レベル `session_*` や承認・設定APIを呼んでもハブで拒否し、WebChat専用の直接介入を迂回しない。登録外のワーカー／案件ID、任意パス指定も拒否する。
4. 同一Discordチャンネルの複数利用者が短時間に依頼しても、各 `ingress_id` に投稿者・許可状態が紐づき、生成した `request_id` が取り違えられない。発行元が特定できないツール呼び出しは拒否する。
5. 受付後からPMへの配送前にユーザー／チャンネルの許可が取り消された場合は新規実行を止める。すでに開始した作業は勝手にロールバックしたと表示せず、WebChatからの停止・承認で扱う。
6. PMからの結果は元のDiscord投稿へ共有可能な構造化要約だけが返り、コード全文・秘密値・生ログを自動投稿しない。Macの通常承認フローが維持され、Discordから `approval_answer` を実行できない。
7. OSSの初期設定では `work_request_policy=disabled`。Q9/Aによる有効化は管理者の明示設定と受入試験を必須とする。Channels上のツール呼び出しと入力帰属の照合は実機検証事項とする。

## 15. Q11/A の追加受入条件（追加着手承認なし・既存ツール承認のみ）

1. 許可済みDiscord投稿者がQ8/A・Q9/Aの条件を満たす通常の調査・実装依頼を送ると、WebChatの追加着手承認なしに `project_pm_send` → `pm_send` へ進み、案件PMが作業を開始できる。
2. 同じ条件で本番デプロイ・大量削除・外部送信などの高影響な依頼を送っても、Hanniganがリスクだけを理由に追加の着手承認カードや承認待ちキューを作らない。**ただし既存Claude Code側の権限判定まで省略しない。**
3. PM／子のClaude Codeが通常のツール許可を求めた場合は、Discord返信ではなく従来のWebChat承認UIに届き、承認されるまで当該ツール操作を進めない。CUアプリ許可・フォルダ信頼などの既存端末確認も従来の扱いを維持する。
4. Claude Codeの設定上すでに自動許可されているツールは、Hannigan独自の承認なしに実行され得る。`permission_mode` や `allowed_tools` をDiscord起点で変更しない。`bypassPermissions` 相当の新規付与や、承認リレーの自動回答を追加しない。
5. 無許可ユーザー／チャンネル、トリガー不成立、DM、発行元不明、登録外案件、委任ポリシー無効の依頼はQ11/Aを理由に通過させない。Discordの直接セッション操作・停止・承認APIは引き続き拒否される。
6. `delivered`／`queued`／`awaiting_approval`／`working`／`completed` を取り違えず、受付時点では実行成功・完了と表示しない。高影響な操作を人間が事前確認できると誤認させる文言も表示しない。

## 16. Q12/C の追加受入条件（期限付き自動配送・失効通知）

1. Discord許可依頼とWebChat秘書経由依頼で対象Macがオフラインの場合、VPSへ永続記録し `pending_offline`／`expires_at` を元窓口へ返す。Discordの許可条件とQ11/Aの「追加着手承認なし」は維持する。
2. WebChatからPM／子へ直接投稿し対象Macがオフラインなら、同じ期限付き保留へ入り、子の担当PM通知はMacが有効指示を実際に受け付ける際に一体登録される。
3. 期限内にMacが復帰し、ブリッジが準備でき、元発行者・Discordチャンネル・案件・セッションの認可がなお有効なら、一度だけ自動配送を試みる。着手承認カードは作らず、Claude既存のツール承認のみ使う。
4. 失効後の再接続、PM起動が遅れた場合、Mac側で流し込み直前に期限超過した場合はすべて実行しない。期限判定にはVPSのUTC時刻を正として扱い、Macの時計ずれ・再接続競合も試験する。
5. 同じ依頼IDの重複投入、ハブ再起動、Mac再起動、WSS切断からの再接続でも二重配送しない。流し込み済みか曖昧なら `delivery_unknown` とし、盲目的な再実行を行わない。
6. `expired`、`cancelled`、`delivery_unknown` は作業完了と区別され、WebChatで状態と履歴を確認できる。元Discord通知は許可再検査に通ったサーバーチャンネルだけへ送る（DM不可）。
7. 許可ユーザー／チャンネルの削除、案件無効化、元の子セッション消失、待機上限到達時は自動配送しない。他案件・別スレッドへの推測配送は禁止。
8. 復帰前から存在する別の作業と競合する可能性をWebChatへ表示する。**Q12/Cの保留機構だけでは同時編集を防げないため、Q14/BによりMac側の実行制御を必須とする。**
9. **Q13/Cにより確定した期限の試験:** `ttl_minutes` 省略時は1,440分、明示設定も正の整数のみ。受付から23時間59分59秒後の有効配送と24時間ちょうど以降の拒否、VPS再起動・再送後に元の `expires_at` を保持すること、期限内に配送済みの作業が24時間到来だけで中断されないことを試験する。**機能全体は設計のみで未検証**。


## 17. Q14/B の追加受入条件（FIFO・並列・CU／編集競合）

1. Mac復帰時に案件A、B、A、Cへの4件が保留されていたら、VPSが受付順にMacへ送り、Macは同順に永続受理する。後着のオンライン依頼が先に割り込まない。再起動しても並びは変わらない。
2. 先頭が長時間実行中でも、別の独立した案件・作業領域の仕事を並列に開始できる（`max_sessions` の上限内）。同一PMへの入力順と `request_id` の報告帰属は維持し、完了順が入れ替わっても誤配信しない。
3. 同じMacでCUを必要とする2つの作業が重なると、後続が `resource_wait(cu_busy)` となり、同時に純正CUを使わない。所有セッションが終了して解放確認後に次が進む。復旧時に所有者不明なら**解放済みと推測せず**保留する。
4. PMと子、複数子、別名／シンボリックリンクで同じ実体領域を指す案件の**同時書込が抑止**される。ツール制限が効かない場合は安全に直列化または作業を拒否する。Q15/Bで共有フォルダ＋単一ライター方式を採用し、実際の書込禁止強制力を検証する。
5. Macは受理したがCU／領域待ちのまま24時間のTTLを超えた依頼は、Claudeに流し込まれず `expired` になる。失効通知、重複排除、再接続や強制停止後のリソース記録復元を検証する。
6. CU／書込の調整待ちは `awaiting_approval` ではなく `resource_wait` と表示。Q11/Aの追加着手承認は生成しない。


## 18. Q15/B の追加受入条件（共有作業領域の書込直列化）

1. PMと子が同じ `projects[].path` の実体ファイルを参照し、新しいworktree・別ブランチ・子専用コピーを自動作成しない。
2. 同一領域に対する PM→子、子→PM、子→子 の同時書込が、Edit/Write/Bash・バックグラウンド処理も含めて技術的に拒否または安全に待機される。
3. 同一／別名／シンボリックリンク／親子関係のパスが重複した場合も単一ライターとなる。異なる安全な領域では並列化できる。
4. 読取専用セッションとの並列動作は、全書込経路が実際に封じられる試験を通った場合だけ有効。通らなければ保守的な直列運用に落とす。
5. ロック所有者が不明／Macが再起動／子が異常終了した場合、推測でロックを外さず `resource_unknown` または `resource_wait` とする。Q16/Aの安全確認が満たされない限り自動解放に成功したとは宣言しない。
6. 24時間の未投入期限、元依頼への報告帰属、Q11/Aの着手承認なし、Mac単位のCU排他を維持する。

## 19. Q16/A の追加受入条件（作業完了時の書込権自動解放）

1. PM自身が編集完了後、セッションと会話履歴を保持したまま書込権を安全確認後に自動返却し、待機中の子が取得できる。子→PM、子→別の子でも同じ。
2. `reply` のみ・`ready` 表示のみ・部分報告・ツール／非同期Bashの進行中には解放しない。プロセスが終了しただけで安全確認が足りない場合も解放しない。
3. 書込権返却後も前所有セッションは生存可能だが、再取得前のEdit/Write/Bash・子プロセス等による書込が技術的に不可能であることを検証する。
4. `release_pending` の途中でデーモンやホストがクラッシュしても、古い書込経路と新しい所有者の同時許可が起きない。所有・世代の照合に失敗したら `resource_unknown` とし、勝手に解放しない。
5. 資源待ち中の未投入依頼は元の `expires_at` を引き継ぐ。待機から解放後の配送でも期限切れ／認可取り消しを再検査し、失効したものを流し込まない。
6. 本機能は書込権のみが対象で、純正CUをタスク終了で解放しない。新たなHannigan独自着手承認も増設しない。
7. 上記がmacOS/Claude Code実機で強制できない場合は自動解放の成功を表示せず、安全な直列実行へ縮退する。Q16/Aは要件の決定であり、実装済みではない。

## 20. Q17/B の追加受入条件（異常時の安全な自動復旧）

1. 子セッションのクラッシュで、旧所有者と全派生書込プロセスの停止・書込不能化が**確認できた場合のみ**自動で安全解放し、後続の書込権取得に進める。証跡を残し、古い所有者からの再書込は拒否する。
2. セッションが応答しないがプロセスが存続している場合、モデルの無応答・タイムアウトだけを理由に書込権を奪わない。異常タスクの再実行や自動 `Esc`・`/exit`・killを行わず、同じ領域の後続は待機させる。
3. Mac／デーモン再起動、ブリッジ再接続、子プロセス情報欠損、権限剥奪失敗、`release_pending` 途中クラッシュでは、保存された `lease_epoch` と実状態を再照合する。不一致・証明不足なら `resource_unknown` を永続化し、**自動解放しない**。
4. WebChatへ要確認通知を記録し、切断後の再読込でも未解決の異常・対象案件・資源・理由・再検証結果を見られる。同じ異常のイベント再送で警告が無制限増殖しない。内部絶対パス・認証情報は通知に含めない。
5. `resource_unknown` の資源で後続のPM／子の書込が並行実行されない一方、競合しない案件は稼働できる。未投入の24時間TTLは進み、期限切れの依頼を復旧後に流し込まない。
6. Q16/Aの正常完了時自動解放とQ14/BのCU専用排他を保つ。Q17/Bは**手動の強制停止権限を新たに与える決定ではない**。人間が復旧できるUI操作の具体的な範囲はQ18で決める。
7. 以上は設計・受入基準。全書込経路の検証・安全解放・UI通知・自動復旧についてmacOS実機と障害注入試験を通すまで**実装済み／動作保証済みとは扱わない**。
