# T11: Remote Control × 純正 Computer Use のアプリ承認

状態: **実施済み（2026-10-14、利用者がスマホで操作）**。結果は「届かない」。
準備日: 2026-10-13 / 実施日: 2026-10-14 06:44〜06:47 JST（Claude Code v2.1.296、Fable 5.1）

## 1. 確かめたいこと

純正 Computer Use（以下 CU）のアプリ承認「Computer Use wants to control these apps」は、Channels の承認中継には届かない（第 2 回検証 T05、T08）。
Remote Control でつないだスマホや claude.ai/code に、この承認が届いて許可・拒否できるかを確かめる。

結果は Phase 3 の補助経路（tmux 画面の読み取りと選択キー送信）の範囲を決める。

| T11 の結果 | 補助経路で扱うもの |
| --- | --- |
| 届いて回答できる | 開発用チャネル警告とフォルダの信頼確認だけ。CU 承認は Remote Control に任せる選択肢が増える |
| 届かない | 上の 2 つに加えて CU 承認も補助経路で扱う（Phase 2 で実装済みの画面読み取りをそのまま使う） |

どちらの結果でも、開発用チャネル警告は端末にしか出ないため補助経路は必要になる。
Phase 2 はこの前提で画面読み取りを実装した。T11 が決めるのは CU 承認を補助経路で扱うかどうかだけである。

## 2. 公式資料で分かっていること（2026-10-13 確認）

- 出典: [Remote Control](https://code.claude.com/docs/en/remote-control)
- `claude --remote-control [name]` で対話セッションを Remote Control つきで起動できる
- 権限の確認と `AskUserQuestion` は、回答されるまで開いたまま遠隔に出る
- 「それ以外の種類のダイアログ」も遠隔に転送されることがあり、既定では 5 分で閉じて何もしない既定の選択肢で続く（`dialogExpiry` で変更可）
- CU のアプリ承認がどの扱いになるかは書かれていない。だから実測が要る

## 3. 準備

- CLI の組み込み CU が試験フォルダ（既定 `~/hannigan-t11`）で有効。有効化はフォルダ単位で、手順 1 の後に端末で `/mcp` → `computer-use` → Enable を一度行う。Claude デスクトップアプリの「コンピューター使用」設定は別物で、CLI には反映されない（2026-10-14 時点、`~/.claude.json` の `projects.<path>.enabledMcpServers` で確認）
- ターミナル（tmux を動かすアプリ、通常は Terminal.app）にアクセシビリティと画面収録が付与済み。デスクトップアプリへの付与とは別に要る
- スマホの Claude アプリに同じアカウントでログイン済み
- 利用枠に余裕がある（短い会話 2 回程度）

## 4. 手順

1. ターミナルで次を実行する

   ```bash
   scripts/t11-start.sh
   tmux attach -t hn-t11
   ```

2. 端末に Remote Control の接続表示（`/rc active` など）が出たら、`Ctrl-b d` で tmux から離れる。**以後は端末に触らない**
3. スマホの Claude アプリで Code を開き、`hannigan-T11` のセッションを選ぶ
4. スマホから次を送る

   ```text
   computer-use の request_access で com.apple.TextEdit の利用を求めて、許可されたら新規書類に「T11-<今の時刻>」と入力して。
   ```

5. スマホの画面を観察し、次を記録する（スクリーンショットを推奨）
   - アプリ承認がスマホに出たか。出たなら選択肢の文言
   - スマホで「許可」を選べたか。選んだ後に TextEdit へ入力されたか
   - 出なかった場合、何分待ったか。スマホ側の表示はどうだったか
6. 端末側の記録を取る

   ```bash
   tmux capture-pane -p -t hn-t11 -S -200 > docs/verification/t11-remote-control-cu/pane-$(date +%H%M%S).txt
   ```

7. 拒否の確認として、手順 4 をもう一度送り、スマホで拒否を選べるかを見る（承認済みなら `/exit` で終えて手順 1 からやり直す）
8. 比較として、スマホから「`ls` を Bash で実行して」と送り、通常ツールの承認がスマホに出ることを確かめる
9. 片付け: `tmux send-keys -t hn-t11 /exit Enter`。TextEdit の試験用書類を保存せずに閉じる

## 5. 結果

実施者は利用者で、スマホの Claude アプリから操作した。記録は利用者の報告と端末画面（[`evidence/pane-final.txt`](evidence/pane-final.txt)、利用者名とセッション URL は伏せた）による。

| 項目 | 結果 | 証拠 |
| --- | --- | --- |
| CU アプリ承認がスマホに出たか | 出なかった | 利用者の報告 |
| スマホから許可できたか | できなかった。承認は Mac のターミナルに出て、端末で許可した | 利用者の報告。端末画面で `request_access` の後に「許可もらえたよ」 |
| スマホから拒否できたか | 未確認（承認がスマホに出ないため試す場面がない） | |
| 端末側のダイアログはどうなったか | 端末にだけ出た。許可後は同じ会話の中で、追加の承認なしに TextEdit へ何度も入力できた（`T11-06:45:17` と `あいうえを`） | `evidence/pane-final.txt` |
| 新しいスレッドでの扱い | スマホで新しいスレッドを作ると、そこでも CU 承認が再び端末に出た。承認はスレッド（セッション）単位 | 利用者の報告 |
| 通常ツールの承認はスマホに出たか（比較） | 未確認 | |
| 判定 | **届かない**。CU アプリ承認は Remote Control でも端末にしか出ない | |

分かったことを次にまとめる。

- CU のアプリ承認は Channels の承認中継にも Remote Control にも届かない。端末の画面読み取りが唯一の遠隔回答の手段になる
- 承認の有効範囲はセッション単位で、第 2 回検証 T10（再開で再承認）とも合う。新しいセッションを作るたび、最初の CU 利用で承認が 1 回要る
- このため Hannigan は CU 承認を補助経路（Phase 2 で実装済みの `cu_app_approval` の画面読み取り）で扱う。本物の CU 承認画面での WebChat 回答は Phase 3 で確かめる

その他の観察として、利用者設定のフック（`claudecode-monitor/hooks/claude-code-hook.sh`）が見つからないエラーが毎ツールで出たが、動作は止まらなかった。実施時点で 5 時間枠の利用は 99% だった。スマホアプリの版は記録していない。
